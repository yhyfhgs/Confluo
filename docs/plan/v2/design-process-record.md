## 0. 摘要

1. **过程**：
   - 调研 workflow 于 2026-09-26（UTC）完成；简报与设计 workflow 于 2026-09-27 执行。本文写作时，设计 workflow 只剩 09 路线图与本文两个任务。
   - 两个 workflow 都因会话用量上限中断过，都从断点续做完成。
   - 全部 subagent 使用 Opus 5.5（max effort）。
2. **调研**：
   - 共 29 个 agent：14 个主题调研、14 个逐篇对抗核验、1 个综合。
   - 产出 14 篇调研（共 13,066 行）和 1 篇综合。
   - 核验约 797 组承重断言，就地修正约 150–160 处，删除 0 处。
3. **简报**：主 agent 起草简报后，按综合 §8 的一致性核对做了修订，作为设计阶段的上游约束。主要修订有三处：
   - P-03 改为取回在用户侧执行；
   - 凭证分为部署级与用户级；
   - 更正 TSRG 近似界的措辞。
4. **设计**：共 26 个任务。
   - 首轮完成 9 篇起草与 7 次评审（16/26）后，额度用尽而中断。
   - 主 agent 汇总约 60 项跨文档问题，写成简报 §10 的 R2-01…R2-50，并归档首轮返回。
   - 续跑完成了 5 次评审、demo 的构建与评审和一致性审计。09 路线图与本文是续跑的最后两个任务；本文写作时 09 尚未落盘。
   - 产物：9 篇文档共 20,812 行、10 张配图、1 个单文件 demo。
5. **评审**：
   - 12 次文档评审共发现 351 个问题，就地修复 325 个（92.6%）。评审表中标"高"的有 56 行。
   - 高严重度问题集中在三类：算法与伪代码无法落地（04、06）；出站与事件接入的正确性（02）；私有数据流入共享层的隐蔽路径（04、06）。
   - demo 评审发现 34 个问题，修复 29 个。
6. **审计**：一次一致性审计把 50 条裁决逐条落实到 9 篇文档，并列出 11 项遗留（§6.3）。本文另核出 3 处审计没有列出的残留（§6.4）。
7. **待裁决**：去重后共 55 项（§7）。
   - 按级别：P0 8 项、P1 26 项、P2 21 项。
   - 按决策方：主 agent 32 项、用户 11 项、法务与外部 8 项、09 与登记 4 项。
   - 最急的是四件事：robots ADR 的统一前提；三份 P0 发函（NCBI、EBI、OpenReview）；法务问题 LQ-07、LQ-01、LQ-02、LQ-05、LQ-17；B 类摘要遇到自然语言 TDM 保留时怎么处置。

### 2.2 调研 workflow（2026-09-26，UTC）

- **编排**：分三个阶段，依次是主题并行调研、逐篇对抗核验、综合。14 个主题按用户的五项需求划分（综合 §1.1）：
  - 来源 5 篇：NS、LS、SS、CS、AG；
  - 开源 2 篇：OSS、RO；
  - 市场 1 篇：MK；
  - 算法 4 篇：SM、SR、RT、PU；
  - 交互 1 篇：UX；
  - 合规 1 篇：CP。
- **规模**（综合 §0、§3、§5–§7）：
  - 14 篇共 13,066 行；
  - 5 篇来源调研共登记 249 行，合并去重后得到 187 行候选来源；
  - 设计输入 SI-01…SI-70，共 70 条；
  - CP 的 28 条硬约束 HC-01…HC-28；
  - 张力 T1–T18，共 18 项；
  - 调研缺口 G-01…G-16，共 16 项。
- **核验统计**（综合 §0 第 1 条、§1.3）：
  - 约 797 组承重断言，就地修正约 150–160 处（各篇计数口径不一），删除 0 处；
  - 14 篇都没有发现编造的仓库、论文、公司或数字。
- **中断与续做**（survey README §3）：
  - market、recommendation-oss、social-media 三篇的核验各中断过一次。market 注明原因是会话用量上限，另两篇没有写原因。中断后由续核验复核首轮改动再合并，没有留下半截修改。
  - 综合也因一次会话用量上限中断，之后续做完成。
  - 会话共享的 WebSearch 配额用尽后，部分篇改用 curl、`gh api` 或官方 API 直读。
- **请求纪律的偏差**：各篇自行披露，综合 §1.5 汇总如下。
  - NS 有 2 次请求落在 robots 禁区；
  - AG 有 9 次请求发生在读取 robots 之前；
  - SS 读到 `Disallow: /` 之后仍发出 1 次请求，另有 2 次发往 api.osf.io；
  - CS 访问了禁止 Claude 类 agent 的 ICORE 门户，并误发 1 次请求。

  这些偏差是 SI-38（robots 先行闸由框架强制执行）的依据，也是 02 AD-01"Egress Gateway 为唯一出口"的理由之一（02 §8-2）。
- **凭证**：调研期间没有使用用户的机构凭证或出版商账号（survey README §3）。

### 2.3 简报：起草与按综合 §8 修订（2026-09-27）

- **起草与核对**：主 agent 起草了简报初稿。综合 agent 运行时已经能读到这份初稿（综合 §1.5 记为"仅读取，未改动"），并在综合 §8 逐条核对：多数条目"一致"，若干条目"建议细化"，另有 3 处"需复核"：
  - P-03 的"本人会话"可能被读成服务器持有用户 cookie 代为取回，这与 CP HC-03 冲突；
  - §6.2-2 中 TSRG 近似界的措辞；
  - §6.3-3 的凭证方案：服务端 KMS 封装与客户端加密属于两种信任模型。
- **修订**：主 agent 据此修订（简报 §0 修订表第 3 行）：
  - P-03 改为取回在用户侧执行；
  - 凭证分为部署级与用户级，用户级出版商凭证端到端加密；
  - 更正 TSRG 近似界的措辞；
  - 补充 Crossref 增量的主次、bulk 主机的 robots、B 类摘要的限制、pg_textsearch 为默认、LLM 数据出境、ADR 候选 9–13，以及 Q7 的许可更新。
- **修订后的简报确定了**：产品定义、B-01…B-06、P-01…P-09、统一术语、各子系统裁决、13 项 ADR 候选、Q1–Q7 的默认假设，以及文档分工与接口归属（简报 §2–§9）。简报要求各文档"不得静默偏离"。
- **修订表的顺序**：简报 §0 修订表把"按综合 §8 修订"排在"新增 §10"之后。但从内容和各文档首轮稿的引用看，这次修订发生在设计 workflow 之前。建议在修订表中补上时刻，见 DPR-22。

### 2.6 断点续跑

续跑任务的输入是简报（含 §10）、首轮 JSON 与各文档当前稿，只运行首轮没有完成的 10 个任务。任务之间的先后，按依赖关系与文件时间推断：

1. 04 FEAS 评审；
2. 04 EVID 评审（在 FEAS 之后，记为 04 的第 2 轮）；
3. 05 FEAS+EVID 评审；
4. 06 USER+EVID 评审（06 的第 2 轮）；
5. 07 FEAS+EVID 评审（07 的第 2 轮）；
6. demo 构建；
7. demo 评审；
8. 一致性审计；
9. 09 路线图与 ADR 草案（本文写作时尚未落盘）；
10. 本过程记录。

续跑中与第 2 轮裁决的对齐：

- 5 次评审都把 R2 对齐列为核对项，各自的评审记录列出了对齐的 R2 编号；
- demo 按 R2-42 实现了 15/25/35 三档与"候选不足时提前结束"，按 R2-49、R2-50 实现了入口；

## 3. 方法：为什么这样编排

下面的编排理由，依据 [AGENTS.md](../../../AGENTS.md)、survey README 与各轮的实际产出归纳而来。

### 3.1 多模态调研

这里的"多模态"指取证方式的多样，而不是单一的网页检索（survey README §2、§3）：

| 取证方式 | 例子 | 留存形式 |
|---|---|---|
| 一手阅读官方文档与条款 | ToS、robots.txt、API 文档、许可正文、法规原文 | 各篇"参考来源"，带访问日期 |
| 实测官方 API 与站点 | NS 107 行刊级实测；AG 204 刊的摘要覆盖与 12 个 CS 会议的 Crossref 检查；PU 实测 E1–E8，并留有 225 次外部请求的台账 | 同名子目录中的请求台账与实测文件 |
| 批量采集仓库元数据 | OSS 调研 197 项开源，另批量复测 196 个仓库的 star、许可与归档状态 | repo-metrics TSV |
| 文献与产品调研 | 学术推荐论文；社媒推荐的官方与民间材料（分证据等级）；约 66 个产品 | 各篇"证据分级"节 |
| 本地证据 | v1 代码、VenueSpec、设计文档与 ADR | 仓库路径 |

**理由**：v2 的难点同时牵涉来源条款、算法、交互与监管。只靠单一来源，容易把二手说法当成事实。多种取证互相印证，每条事实都带出处与日期，才能按引用规范（survey README §4）区分"确认""⚠ 未核验""◐""⚠ 推断"。

### 3.2 对抗核验

- **做法**：每篇调研由一个独立的 Verify agent 复核（综合 §1.2）。
  - 默认怀疑，只认一手来源；
  - 错误就地修正，标注"核验修正"或"核验补充"；
  - 文末写唯一的"核验记录"节。
- **理由**：设计阶段要把调研事实写进需求与 ADR。引用规范禁止把带 ⚠ 或 ◐ 的事实写成确定性条款（survey README §4-3），所以必须先确定承重断言的证据等级。
- **效果**：
  - 约 797 组断言中修正约 150–160 处，删除 0 处。
  - 综合 §1.3 列出了对设计影响最大的 12 条修正，例如：Crossref 自 2025-12-01 起按请求类型分池；MSC2020 的许可为 CC BY-NC-SA；NCBI 与 EBI 的 bulk 主机 robots 全禁；Motion 的默认弹簧不收敛。
  - 这些修正后来直接成为简报与设计的约束，例如 R2-13、R2-22，以及 07 的显式弹簧参数。

### 3.3 主 agent 裁决：简报与第 2 轮裁决

- **分工依据**：AGENTS.md 规定，有边界的研究交给 subagent 并给出明确的输出路径，由主 agent 审查证据、对最终的架构与设计决策负责。因此 subagent 只写分配给自己的文件；架构取舍由主 agent 书面裁决，首轮前写在简报中，首轮后写在 §10 中。
- **防止静默偏离的两道机制**：
  1. 各文档必须在"异议与备选"中写出对简报的偏离及其证据；
  2. 评审把"静默细化"当作问题处理。例如，名录的 COVER 评审发现 biorxiv 等来源改以 Crossref 为首选，却没有记入异议，于是要求补上异议 8。
- **第 2 轮裁决的范围**：只处理跨文档冲突与异议，不重写各文档。各文档按 §10 自行对齐，再由审计复核。

## 8. 经验与后续建议

### 8.1 有效的做法

1. **先定证据等级，再做设计。**
   - 调研阶段约 797 组承重断言经对抗核验，删除 0 处，修正约 150–160 处。
   - 设计评审在引用处仍发现证据问题，例如 EPMC 的 Crawl-Delay、S2 bulk 的排序方式、cs.LG 周量的误读。这说明"引用时再核一次"仍有必要。
2. **分视角评审各有不可替代的发现。**
   - FEAS 发现的问题作者自己难以发现：覆盖素描使联邦永不触发、最小费用流的弧设计、分区表上的 `ON CONFLICT`、R5 按需放行不可达。
   - EVID 找出了两处私有数据流入共享层的隐蔽路径（04 的路由输入、06 的读者向量）。
   - USER 抓住了文案陷阱（"稍后"）与交互断点。
   - COVER 查出了静默细化与计数错误。
3. **结构化返回使中断可以恢复。**
   - 首轮 16 份返回含 53 条"未解决"与 143 条作者待决。
   - 主 agent 不必重读全文，就能汇总约 60 项问题，并一次给出 50 条裁决。
   - 续跑评审逐条引用 R2 编号来对齐。
4. **"归属方优先"加机械核查，使审计可以收敛。** 一次审计就把 50 条裁决落实到 9 篇文档，并用脚本核对了编号、表列、链接与事件名。
5. **评审中补查一手来源。** 补查的来源包括：
   - RFC 9309；
   - PG18 文档与 `pg_proc.dat`；
   - GitHub 许可接口；
   - Hugging Face 模型卡；
   - OR-Tools 的 LICENSE 原文；
   - OpenAlex 按 PMID 单查的实测（2 次请求，先读 robots）。

   这些补查关闭了若干 ⚠。

### 8.2 暴露的问题

1. **并行起草时读到对方的旧稿。** 05 与 08 的留存值、许可码形态互相引用了对方的旧稿，只能靠后续的评审与审计纠正。
2. **中断时正在运行的任务留下"无记录的改动"。** 04 的首次可行性评审改动了正文，但既没有返回结果，也没有写评审记录。
3. **R2 前后的评审不对称。**
   - 01、02、03、08 与名录的评审都在 R2 之前完成，它们的 R2 对齐只由一次审计完成，之后没有再经评审。
   - 04、05、06、07 在续跑中按 R2 逐条核对过。
4. **权限边界留下了残留。**
   - 审计无权修改配图，4 张配图仍是旧口径。
   - 跨文档请求（06 的 AL 表、07 的 X 表、各文档 §20 中的请求）没有统一台账，AL-24 的两项在审计之后仍未落地。
5. **demo 评审没有在浏览器中渲染。** demo 评审者按任务要求不做浏览器渲染，新增的画廊与图区未经渲染验证。本文只补做了有限的冒烟检查。
6. **文档体量大。**
   - 9 篇合计约 2.08 万行、约 2.4 MB，单篇最长 3,339 行，评审与审计的阅读成本高。
   - 各文档的 AC 占位编号互相重复，09 改号的工作量不小。
