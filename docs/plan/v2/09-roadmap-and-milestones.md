# 09 · v2 实施路线图与里程碑

> **定位**：v2 重新设计阶段的实施计划，回答"先做什么、做到什么算完、谁来验、何时要用户拍板"。上游约束是[设计决策简报](00-design-brief.md)（以下简称"简报"，§10 第 2 轮裁决优先），需求与编号来自 [01](01-vision-and-requirements.md)，各子系统方案来自 [02](02-architecture.md)–[08](08-compliance-security-privacy.md) 与[支持名录](../../catalog/source-directory.md)，证据层是[调研综合](../../survey/00-survey-synthesis.md)（以下简称"综合"）与 14 篇调研（均于 2026-09-26 经对抗式核验）。本文不含实现代码，代码块均为**设计伪代码**。
> **本文定义**（简报 §9）：里程碑 V0…V7、任务卡、正式验收编号 `AC-V<m>.<n>`、风险登记与决策门。ADR 草案 D-040…D-071 另见 [adr-proposals](adr-proposals.md)。
> **本文不定义**：FR/NFR 编号与术语（01）、HC 编号与合规细则（08）、组件与 API（02）、SourceSpec 与语料流水线（03）、检索与路由（04）、DDL（05）、事件契约与推荐算法（06）、交互规范（07）。
> **引用写法**：沿用 [survey README §4](../../survey/README.md)：`SI-xx` 指综合 §6.1 的设计输入，`G-01…G-16` 指综合 §7.3 的调研缺口，`HC-xx` 以 08 §2 的登记为准。设计文档的正式验收编号写作 `AC-V<m>.<n>`；它们的起草期占位 `AC-V?.n` 已全部回填（新旧对照见附录 A）。
> **默认假设**：简报 §8 的 Q1–Q7 尚待用户拍板，本文按默认假设排期，依赖其默认值的条目标注"（默认假设 Qn）"，每个问题的最晚决策时点见 §7。
> **标记**：`⚠` 照录调研或上游文档的未核验标注；"设计目标（草案）"与"[判断]"表示待实现期压测或实验校准的目标值，不是事实断言；人日与日历是规划估算（±50%），不是承诺。

## 0. 结论速览

1. **八个里程碑，先底座后体验**：V0 基线（ADR 与设计定稿、注册表 schema、PG 骨架、策略引擎与出站网关骨架）→ V1 语料底座与 P0 来源 → V2 检索与 TSRG → V3 多用户平台 → V4 推荐 R0 与 Feed API → V5 前端 PWA 与可用性测试 → V6 社交与双向匹配、推荐 R1 → V7 规模化与加固。合规闸门与数据底座先于一切面向用户的能力落地（§2.1）。
2. **v2.0 公开内测 = V5 完成**：此时 01 的 48 条 Must 全部通过验收，AC-0 红线全绿，可用性测试 P0 问题为 0。V6 对应 v2.1（公开评论与评分、研究者匹配、推荐 R1），V7 对应 v2.2（1 万用户容量、SLO、Could 项）（§2.5）。
3. **工作量**：113 张任务卡，合计约 **599 人日**（V0 62、V1 125、V2 78、V3 89、V4 77、V5 83、V6 48、V7 37）。按 3 条并行泳道、含评审与合并的参考日历约 38 周到 V7、约 30 周到 v2.0；外部等待（书面确认、法务、14 日在线观测、7 日内测、真人可用性测试）比编码更决定节奏（§2.6）。
4. **正式验收**：各设计文档 366 个 `AC-V?.n` 草案占位收敛为 **243 条正式 AC**（V0 29、V1 41、V2 46、V3 29、V4 34、V5 46、V6 11、V7 7），跨文档同一判据合并为同一编号、同一文档内不重号；已直接回填到 01–08 与名录（只改编号不改语义，附录 A）。AC-0 红线 AC-0.1…AC-0.18 按 08 §17.1 定稿，贯穿全部里程碑（§4.1）。
5. **需求全覆盖**：FR-17…FR-87 与 NFR-9…NFR-27 共 90 条，每条至少映射到 1 条正式 AC（§4.2、§4.3）。
6. **v1 双轨**：v1 CLI 与 SQLite 在 V0 打 `v1-final` 后维护冻结、持续可用；v2 在同一仓库新目录中开发，v1 代码只以只读 ETL 源与 pc-agent 复用库的身份参与；迁移分 9 步，每步可回滚，任何一步都不写 v1 库（§6）。
7. **决策门**：Q4（robots 与文档化 API 冲突）须在 V1 开工前确认；Q7（表示模型）在 V1 出口定型，V2 建向量索引前必须完成；Q1、Q2 最晚在 V5 公开内测前定案；Q5、Q6 在 V6 前；Q3 在 V7 前或预算触发时（§7）。
8. **补充调研**：G-01…G-16 全部排入里程碑；其中 G-01、G-03、G-06、G-07 是关键路径上的高优先级项（§8）。
9. **Top 10 风险**：上游条款与书面确认迟滞、法务结论缺位、上游计费收紧、分学科表示质量、卡片形态接受度、小样本学习与实验功效、隐私与越权缺陷、CPU 档性能预算、范围与评审吞吐、浏览器与 PWA 平台限制（§9）。
10. **组织方式**：沿用 v1 的"任务卡 + 独立评审 + controller 合并"编排：每卡一分支一实现 agent，另一实例独立评审（安全与合规卡双评审），controller 跑门禁、合并、打里程碑 tag，并留痕到日志、验收记录与里程碑报告（§10）。
11. **ADR**：简报 §7 的 13 项、§10 的 3 项（R2-01、R2-08、R2-41）与各文档候选去重后起草为 32 条 proposed ADR（D-040…D-071），V0 的第一张任务卡就是让用户逐条裁决（[adr-proposals](adr-proposals.md)）。

## 2. 实现方案 ①：总体策略

### 2.1 排序原则

1. **合规闸门先于数据，数据先于算法，算法先于界面**。v2 从"本人工具"变成"平台运营者"，许多 v1 的许可前提失效（CP §2.0）。出站网关、策略引擎、四域与 RLS 的不变式一旦晚于数据落地，就要回头清洗已入库的内容（例如 B 类摘要进了共享派生、`open_fulltext` 进了公共热度）。所以 V0 先立骨架与不变式测试，V1 在闸门之内收割，V3 在 RLS 之内接用户。
2. **本地语料是一切体验的前提**（P-01）。卡片流、LATEST、频道、Percolator 只读本地；联邦只补即席查询的覆盖缺口。V1 的语料底座（快照子集 + 增量收割 + 身份去重 + enrich）是 V2 检索与 V4 推荐的共同输入。
3. **评测先行，决策有据**（P-08）。V1 建分学科金标（每学科 ≥200 条），同一批金标服务 Q7 的表示选型（V1）、检索质量回归门（V2）与推荐离线评测（V4）；V4 第一次下发就记曝光日志并跑 A/A。
4. **最窄竖切，尽早联调**。每个里程碑都产出端到端可运行的切片：V1 可在管理 CLI 中看到按学科入库的论文；V2 可用 API 检索与订阅频道；V4 可用 demo 客户端刷到个性化批次；V5 才把完整界面交给真人测试。前端从 V3 起以 mock API 预研（07 的 E2E 本就以 mock API 为准），不等后端完工。
5. **外部依赖左移**。书面确认发函、法务委托、用户之声调研放在 V0；它们的结论在 V1–V3 才被需要，但等待期最长。
6. **可降级是完成的一部分**（P-09）。每个能力的 DoD 都包含它的降级路径：替补链（AC-V1.21）、联邦部分失败（AC-V2.33）、非个性化回退（AC-V4.1）、LLM 全不可用（AC-V4.28）。

**备选排序**（未采纳）：① 前端先行（先做 PWA 与 demo 数据，再补后端）——可更早拿到交互反馈，但 demo 已在设计阶段交付并做可用性测试（AC-V0.10），再往前推只会让界面建立在未定的事件契约与批块协议上；② 推荐与检索并行于语料底座——会让金标与表示选型失去共同基线。二者都保留为局部做法：前端以 mock API 预研，检索与推荐的算法原型可在 V1 期间用快照样本离线开发。

## 3. 里程碑详述 ②

### 3.0 读法与通用 DoD

每个里程碑按固定结构书写：目标 → 范围（做 / 不做）→ 交付物 → 任务卡 → DoD → 验收标准 → 风险。任务卡表的"承接章节"指向设计文档中的实现方案，"关联 AC"指向本里程碑的正式验收编号。验收表的判据是草案判据的可度量摘要，完整判据以"草案来源"指向的设计文档为准（回填后这些文档里的编号与本表一致）。

**通用 DoD**（每个里程碑都必须满足，下文只列各自的专项 DoD）：

1. 本里程碑全部任务卡已合并；每张卡经独立评审 APPROVE，无未关闭的 P0/P1 评审意见（§10.3）。
2. 本里程碑全部 `AC-V<m>.*` 判定为通过，逐条证据写入 `docs/testing/records/YYYY-MM-DD-v2-v<m>-acceptance.md`；适用的 AC-0 全绿（§4.1）。判为"有条件通过"的条目须写明条件与关闭期限，且不得是 AC-0 或安全、隐私类条目。
3. `make check` 在断网环境全绿，核心覆盖率 ≥80%；新增的在线、浏览器、压测用例都有门控标记。
4. 已 `stable` 模块对应的设计章节状态更新；新增或变更的文档同步 INDEX；新增共享术语同步 GLOSSARY。
5. 里程碑报告与 session 日志落盘；progress.md 的里程碑与模块状态表更新；打 tag `v2-v<m>`。
6. 下一里程碑的决策门（§7）已关闭，或已记录按默认假设继续的理由。

### 3.4 V3 多用户平台

**目标**：把单租户的底座变成可邀请他人使用的多用户平台：账号与认证、RLS 全覆盖、事件接入、数据导出与删除、用户侧取回（扩展与 pc-agent）、端到端凭证、管理员控制台、备份恢复与 v1 ETL。

- 做：账号、会话、ORCID OAuth、MFA、年龄声明、同意；`usr` 全表 RLS 与越权测试；频道、文献库、关注与屏蔽、设置；事件接入与 06 schema 代码生成；DSR（导出、注销、加密粉碎、保留作业）；题录导入与 `k_cf` 门槛；Companion Extension（Chromium 优先）；pc-agent 与 personal 本机取回；端到端凭证库与多设备同步；管理员控制台与来源登记工作流；通知与身份出站经网关；地区单元与特性开关；备份与恢复；安全回归；v1 → v2 完整 ETL；P1 来源第一批（泳道任务）。

### 5.2 门禁与默认离线

## 6. v1 → v2 迁移步骤 ⑤

### 6.1 原则

1. **v1 全程可用**：迁移任何一步都以只读方式访问 v1 库与文件；v1 CLI 在 v2.0 之后继续可用，直到用户主动停用。
2. **每步可回滚**：v2 侧的每一步都写入独立的目标（staging schema、迁移用户、带 `legacy_v1_id` 的行、`ops.etl_v1_map`），回滚就是丢弃这些目标后重跑；v1 侧没有需要回滚的状态。
3. **派生结构不搬运**：BM25、向量、`cluster_id`、`route_stat` 在 PG 侧重建（05 §10.1；RT §10.7）。
4. **权利从严、私有不上云**：无法证明为 A 或 B 类的摘要不进 `corpus`；v1 PDF 与抽取全文只在 personal 且 `host_is_user_device=true` 时进入本机私有空间；v1 凭证不迁往任何服务端（05 §10.1、§10.3；HC-04）。

- 双轨期从 M7 开始，至少持续到 V5 出口；期间 v1 的缺陷修复照常进行，v2 的任何数据问题都能以 v1 库为真值复核。

## 10. 组织方式 ⑨

### 10.1 角色

| 角色 | 由谁担任 | 职责 |
|---|---|---|
| 用户 | 仓库所有者 | 裁决 ADR（D-040…D-071 的 accepted）、Q1–Q7、法务与对外事项（发函签名、商用许可）；确认里程碑出口 |
| controller | 主 agent | 拥有路线图、里程碑计划与最终架构裁决（AGENTS.md）；拆卡、派卡、排波次；跑门禁、合并、打 tag；主持评审分歧；写里程碑报告 |
| 实现 agent | 按卡指派 | 一卡一分支一 agent；按承接章节实现，附测试、fixture、文档更新与自查清单 |
| 独立评审 agent | 与实现者不同的实例 | 按评审清单亲自构造对抗输入复核；给出 APPROVE / NEEDS_FIX / NEEDS_DECISION；安全、隐私、合规、迁移类卡双评审 |
| 调研 agent | 按缺口指派 | 有界调研，写入指定输出路径（§8），不改设计文档 |

### 10.2 任务卡模板

每张卡在开工前由 controller 写成独立文档段落（里程碑实施计划 `docs/plan/v2/implementation/v<m>-plan.md`，V<m> 开工时创建），字段如下：

```text
设计伪代码（任务卡模板，非实现）
id:          V<m>-T<n>
goal:        一句话目标
scope:       做 / 不做（引用承接章节）
depends_on:  [V<m>-T<k>, ...]；决策门 DG-Qx（若有）
design_refs: 0N §x.y ……（须为 approved 章节）
deliverables: 代码路径、测试路径、fixture、文档更新
acceptance:  [AC-V<m>.<n>, ...]；适用的 AC-0
estimate:    人日
branch:      feat/v2-<scope> | connector/<id> | web/<scope> | ext/<scope> | agent/<scope> | docs/v2-<topic>
model_tier:  设计与安全关键 / 标准实现（§10.5）
review:      单评审 | 双评审（安全、隐私、合规、迁移）
```

### 10.3 独立评审与 controller 合并

1. **实现**：实现 agent 在分支上完成交付，自跑 `make check` 与卡内指定的 T5–T14 目标，提交自查清单（git-workflow §4 的通用、文档、代码、adapter 条目，另加 v2 条目：AC-0 适用项、出站与许可、RLS 与数据流、事件契约一致性）。
2. **评审**：独立评审 agent 不看实现者的解释先读 diff 与承接章节，亲自构造对抗输入与变异测试（沿用 v1 Phase 7 T20 的评审规格）；结论三选一：APPROVE、NEEDS_FIX（附可复现证据）、NEEDS_DECISION（设计问题上交 controller）。
3. **回修与复核**：NEEDS_FIX 回到实现 agent，修后由同一评审复核；两轮未过由 controller 裁决是否拆卡或改派模型档。
4. **合并**：controller 在干净环境亲跑门禁，确认 AC 证据齐全后合并到 `main`；设计文档需实质修改时，先按 status-workflow 降回 review 或走 ADR（D-072 起），不得在实现分支里静默改设计。
5. **里程碑出口**：controller 汇总验收记录，写里程碑报告，组织一次跨卡独立审计（专查卡与卡之间的缝，v1 Phase 7 的 T20 经验表明缺陷多出在缝上），用户确认后打 tag。

### 10.4 波次与并行

- 每个里程碑按依赖拆成 3–5 个波次：W0 地基卡（接口、schema、契约先行）→ W1…Wn 并行卡 → 验收批 → 独立审计与修复批 → 文档收尾。
- 并行规则沿用 git-workflow §1：connector、前端组件等无共享文件的卡天然并行；数据库 schema、事件契约、策略引擎等共享核心的卡串行，先到先合、后者 rebase。
- 泳道任务（P1 来源、前端预研）不在关键路径上，只在不抢占关键路径评审容量时推进。

### 10.5 模型选择

按任务选模型（AGENTS.md）：设计关键、安全与隐私、合规判定、算法（路由、推荐、身份）、迁移与跨卡审计用最强档；connector、界面组件、机械迁移与文档同步用标准档；评审档不低于实现档，安全与合规卡的两名评审至少一名为最强档。

### 10.6 留痕

| 内容 | 位置 |
|---|---|
| 每个工作 session | `docs/logs/YYYY-MM-DD-session-NNN.md` |
| 里程碑实施计划与任务卡 | `docs/plan/v2/implementation/v<m>-plan.md` |
| 验收记录 | `docs/testing/records/YYYY-MM-DD-v2-v<m>-acceptance.md` |

## 13. 验收标准（本文）

本文的验收并入 V0：AC-V0.1（ADR 定稿）、AC-V0.2（设计文档定稿与占位清零）、AC-V0.3（路线图自洽）。AC-V0.3 的校验逻辑如下。

```python
# 设计伪代码（非实现）：路线图自洽校验（V0-T15 实现）
reqs  = parse_requirements("01-vision-and-requirements.md")        # FR-17…FR-87、NFR-9…NFR-27，共 90 条
acs   = parse_ac_tables("09-roadmap-and-milestones.md")            # AC-V0.1…AC-V7.7
cards = parse_task_cards("09-roadmap-and-milestones.md")           # V0-T1…V7-T9
xmap  = parse_appendix_a("09-roadmap-and-milestones.md")           # (文档, 原序号) → 正式编号
docs  = ["01", "02", "03", "04", "05", "06", "07", "08", "catalog"]

assert all(len(r.acs) >= 1 for r in reqs)                           # 每条需求至少 1 条 AC
assert all(ac.milestone == int(ac.id.split(".")[0][4:]) for ac in acs)   # 编号中的 V<m> 即归属里程碑
assert unique(ac.id for ac in acs)
assert len(xmap) == 366 and set(xmap.values()) <= {ac.id for ac in acs}
for d in docs:
    text = read(d)
    assert not re.search(r"AC-V\?\.\d", text)                      # 数字占位残留为 0
    own = [xmap[(d, n)] for n in drafts_of(d)]
    assert len(own) == len(set(own))                               # 同一文档内不重号
    assert set(ac_refs(text)) <= {ac.id for ac in acs}             # 文中引用的编号都存在
for c in cards:
    assert c.depends_on is not None and c.estimate > 0 and c.design_refs
    assert all(ref_exists(r) for r in c.design_refs)               # 承接章节存在
    assert all(a in {ac.id for ac in acs} for a in c.acceptance)
must = [r for r in reqs if r.priority == "Must"]
assert all(max(ac.milestone for ac in r.acs) <= 5 for r in must)   # Must 都在 v2.0（V5）之前验收
```

## 16. 异议与备选

1. **里程碑顺序：检索（V2）在多用户（V3）之前**（细化，不是异议）。任务书建议的顺序把 Percolator 与频道放在 V2、账号与 RLS 放在 V3，而频道与 FeedInbox 是 `usr` 域数据。本文的处理：V0 已建 `usr` 域与 RLS 模板，V2 用单租户开发账号（与 personal 部署语义一致）验证频道与 Percolator；V3 再做多用户的 RLS 全覆盖与越权测试。备选是把 V2、V3 合并为一个里程碑，代价是里程碑过大、验收面过宽。V2 与 V3 在日历上本就重叠约 4 周（§2.6）。
2. **02 的"建议里程碑"与本文不同**（细化）。02 §5 把 RLS、单向数据流与出站唯一性都建议在 V0，本文只把后者与角色不变式放在 V0，RLS 全覆盖与数据流金丝雀放在 V3，因为只有 V3 才有真实的多用户数据可测；V0 的 RLS 模板、角色目录断言（AC-V0.21）与静态规则已能让缺陷在 V0–V2 响亮失败。
3. **arXiv 新鲜度的两个草案阈值不一致**（需主 agent 裁定）。03 §17 原第 13 条要求 arXiv 从 OAI 可取到进入 FeedInbox 的 p95 ≤2 小时（AC-V2.41），04 §17 原第 425 条为 ≤3 小时（AC-V2.40，推算公告后约 5.5 小时满足 NFR-12 的 ≤6 小时）。二者不矛盾（≤2 h 蕴含 ≤3 h），但目标口径不同。本文按规则④不合并，两条都保留；建议主 agent 取 04 的 ≤3 h 为验收线、03 的 ≤2 h 为设计目标，并回写 03。
4. **名录 §9.3 原第 6 条早于 R2-16**（需主 agent 确认）。该条仍写"超期通道在 24 小时内被策略引擎置为 `needs_confirmation`"，与简报 R2-16 的 `review_overdue` 30 天宽限不一致。合并进 AC-V1.8 时按 R2-16 判定；名录原文按任务纪律未改，建议由名录维护者按 R2-16 改写。
5. **身份金标精确率阈值**（定稿，不是异议）。03 §17 原第 17 条把自动接受 `version_of` 边的精确率 ≥0.99 列为"建议阈值，09 定稿"，本文定为 0.99（AC-V1.29）。理由：D-007 的"弱信号不自动合并"原则要求错误合并极少；0.99 下候审队列规模须在 V1 报告，若队列不可运维，由 D-048 的版本边投票参数调整，而不是降低阈值。
6. **v2.0 的发布门槛只含 Must**（细化）。Should 项（FR-27、FR-29、FR-30、FR-33、FR-42…FR-44、FR-61、FR-62、FR-65、FR-72…FR-74、FR-82、FR-86）大多在 V3–V5 交付，但 FR-61（社会证明）在 V6，因为它依赖 V6 前的差分隐私决策（简报 R2-04）；FR-62（LLM 增强）的热路径隔离在 V4 验收（AC-V4.28），R1 的画像类 LLM 功能在 V6（AC-V6.9，默认关闭）。若用户要求 v2.0 必含社会证明，须把 DP 决策与 AC-V6.5、AC-V6.6 前移到 V5。
7. **估算的不确定性**（提示）。人日按设计范围与 v1 经验类比，未经团队校准；v1 的实际节奏（Phase 0–7 约 8 天，2026-07-20 至 2026-07-27）表明 agent 编排下编码很快，而 v2 的节奏由外部等待与评审吞吐决定。建议在 V0 出口按实际波次吞吐重估 V1–V7。
